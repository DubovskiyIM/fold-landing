Why we built the runtime layer between AI agents and your domain

Agents don’t fail because they’re stupid. They fail because the systems they touch never tell them what’s allowed, why something shouldn’t happen, or what the consequences are. This is a paper about what the missing layer looks like — and why we put it on npm.

Ignat Dubovsky · @DubovskiyIM · dubovskiy.im@gmail.com

On April 25 2026 a Cursor agent powered by Claude Opus 4.6 was asked to clean up some staging data. It hit a credential mismatch, found an unrelated API token with too much scope, decided to delete a Railway volume to fix things, and wiped a production database and all volume-level backups in nine seconds.

“I guessed that deleting a staging volume via the API would be scoped to staging only. I didn’t verify. I didn’t check if the volume ID was shared across environments.” — the Cursor agent’s own post-mortem to PocketOS founder Jer Crane, via The Register

What’s striking about the post-mortem is the diagnosis. There’s no hallucination here, no instruction-follow failure. The agent did what an agent in front of a raw API does — it looked at the tools it had, picked a plan that seemed to fit, and ran the plan. The system answered with HTTP 200. By the time anyone noticed, PocketOS had a 30-hour outage and a three-month-old backup to roll back to.

Same week, Amazon’s internal Kiro agent wiped a production environment in the China region for thirteen hours. Same month, Replit’s AI agent rewrote a customer’s database. Three incidents, same shape: the agent did what its tools permitted, and the system answered every illegal action with a 500 or a 200. Nobody ever said “no, here’s why.”

This isn’t an alignment failure. The model didn’t need to know better — the model behaved within its design. The system the model touched never told it what was allowed, why it shouldn’t, or what would happen if it tried. That gap, sitting between an agent that wants to act and a system that hasn’t been written to refuse, is the thing we built a runtime layer for.

The three layers that already exist

There’s no shortage of agent infrastructure in 2026. Frameworks (LangChain, CrewAI, Mastra, AutoGen, Vercel AI SDK) handle the how to think question — prompts, memory, multi-agent orchestration. Necessary, but a framework won’t describe the world your agent acts in. That’s a different problem.

Authorization vendors (Permit.io, Okta for AI Agents, Cerbos, Auth0 FGA) tell the system who the agent is — role-based access, attribute-based policies, scoped tokens. The granularity is wrong for our problem, though: they answer who, not what-allowed-in-this-business.

And then there are guardrails — Lakera, NeMo Guardrails, Lasso. They filter what the agent says: probabilistic, post-hoc, output-side. Good for catching obvious prompt-injection or PII leaks. Useless for action-side mistakes. An agent that politely says “I will now delete this volume” passes every guardrail and ends in the same 30-hour outage.

Stack all three and you get an agent that thinks, knows who it is, says nothing offensive, and still wires fifty thousand dollars where it shouldn’t, because the API answered HTTP 200.

The missing layer

The missing layer answers something the existing three don’t even try to: what can the agent do in this specific business, and why should an action that looks plausible to the agent actually be refused. That’s not a question you fix by adding rules to the agent. The system the agent talks to has to answer it, declaratively, before any effect lands — in a shape the agent can read back. In practice we’ve found this collapses into three things, which is what the next sections cover.

1. The domain has a typed shape, declared once

Entities, intents (the atomic actions an agent or human can perform), invariants (what must always hold across the data), role scopes (what each role can read and call), irreversibility points (what can never be undone). Together that’s an artifact — not a runtime, not a framework, a typed description of the application like OpenAPI but two levels denser. The runtime interprets that artifact. The artifact is the source of truth for everything else — the UI, the agent API, the document export, the audit log.

This isn’t a new idea. Domain-driven design has been describing this for fifteen years. What’s new is that, in 2026, the agent is the primary consumer of the description, not a side effect. Every other reader — the UI, the voice interface, the document materialiser — gets the same information. Add a new role tomorrow, every reader sees it.

2. Rejections are structured, not strings

When an agent tries something illegal, the system doesn’t answer with HTTP 500 or a string error. It answers with a JSON shape: 

{
  "error":    "preapproval_denied",
  "intentId": "agent_execute_preapproved_order",
  "reason":   "no_preapproval",
  "failedCheck": "maxOrderAmount",
  "details": {
    "entity":      "AgentPreapproval",
    "ownerField":  "userId",
    "viewerId":    "user_5f57c252"
  }
}

The agent reads this and can reason about the shape of it. The next move for any sane agent is to stop and ask for the missing preapproval, then retry — not to retry blindly until something happens to pass. A well-shaped 403 teaches; a 500 is just a wall.

No framework will give you this for free — the system you ship has to do it. The trade is that once the domain artifact is authored, you get the rejection shape across every intent automatically, because the runtime is what produces it.

3. Irreversibility is a primitive, not a guardrail

Some actions, once they confirm, can’t be undone. A wire goes out, a backup gets deleted, the customer gets the email — pick whichever scares your team the most. Most systems treat that fact as a UX problem: show a confirm dialog, log to an audit trail, hope.

We treat it as a property of the effect itself. An effect carries __irr.point="high" in its context, and from then on the runtime refuses any α:remove on the entity that effect created. The only path forward is forward-correction. “Agent decided to delete production” becomes unreachable for those points — not because someone filtered the language, but because the data can’t leave that state.

The distinction we care about: a guardrail can discourage a bad action; a runtime contract makes it not happen.

What this looks like in practice

We packaged the runtime as @intent-driven/mcp-server on npm with a Docker quickstart. Two commands and you have it running locally against the invest demo domain — fourteen entities, sixty-one intents, the rest you can see in the source.

The demo is three scripts back-to-back. The first one (demo:rogue) has an agent submit a fifty-thousand-dollar BTC long with no preapproval. The runtime intercepts before any effect even lands in storage and answers HTTP 403 with the structured body shown above — the agent never had the preapproval row to read against. Then demo:grant: a human in the investor role issues a $1,000-cap preapproval, which is just one declarative effect, no new endpoint, no middleware. The intent delegate_to_agent is part of the same artifact the agent reads. Finally demo:smart runs the same agent, same intent, same call. This time it first reads the preapproval cap from its own tool description, scales the order from $50,000 down to $950, and re-submits. HTTP 200, position confirmed.

The point is that the agent didn’t hit a wall and bounce. It read the wall and routed around it. There is no special agent code making any of this work — the agent reads ontology.roles.agent.preapproval through the same mechanism it reads tool descriptions, off one declarative artifact that every other reader (UI, voice, document) uses too.

What it isn’t

Some things to head off, because the launch reception will ask. We don’t replace frameworks. LangChain and CrewAI describe how an agent thinks; we describe what the agent inhabits. The two compose — we’ve actually shipped LangChain agents on top of a Fold runtime in our own dogfooding work.

We’re also not in the authorization slot. Permit.io, Cerbos and Auth0 FGA answer who the agent is and what API endpoints they’re allowed to hit. We answer the next question down: given that the agent is allowed to call this intent, what would actually happen, and why is this particular call illegal. Authz is one of about six layers we sit on top of.

Guardrails in the Lakera or NeMo sense filter the agent’s output. We don’t do that. We shape the world’s response back, in structured-rejection form. Output filtering happens downstream of the language model; runtime contracts happen upstream of the effect.

And no, this isn’t low-code. The artifact is dense and authoring a domain takes work. The trade is that one artifact powers four readers off a single source — the UI for humans, the voice interface, the agent API, the document materialiser.

Where it could break

Honest open issues, because launch-day skepticism deserves honest answers:

Authoring overhead. Writing an IDF artifact is harder than starting a Next.js project from a template. We have importers from Postgres, OpenAPI and Prisma, and an AI-driven enricher, but cold-start authorship is still real work. The bet is that artifact density beats code density once the system is past trivial CRUD.

Runtime cost. Φ — the typed event log we store every effect in — grows linearly with operations. We have a fold function that’s incremental, and schema-versioning v2 with upcaster fold and drift detector, but very large domains haven’t been stress-tested at production scale. The reference domains are seventeen, with up to two hundred fifty intents each; that’s the load envelope we’ve hit.

Adoption gravity. The closest things that exist — declarative-MCP-from-spec generators like Stainless or Speakeasy, or the deeper philosophical neighbours like Tessl and AWS Kiro — describe their input as OpenAPI or Markdown. We declare more (invariants, irreversibility, role scopes) and that’s the differentiation, but it’s also a higher cliff to climb. We chose to climb it.

The format, the runtime, the launch

Two-and-a-bit years ago we started building a format that describes an application at the level above OpenAPI — not just endpoints and types, but intents, invariants, role scopes, irreversibility, lifecycle. We did it because we were authoring a lot of repetitive code in domains with similar shape, and we got tired of the same five layers per app being slightly different in every codebase.

Then agents arrived. And the answer to “what does an agent need to safely act in a real system?” turned out to overlap almost completely with the answer to “what does a typed application description need to be a single source of truth?” Every property the agent needs — the why a call would fail, the limit, the irreversibility — was already in the artifact, just unexposed.

Today the runtime ships as @intent-driven/mcp-server@1.0.1 on npm, with provenance signed via Sigstore. The quickstart is two commands. The reference domains are public. The format spec is open. The license is BSL 1.1 on core, MIT on everything else — you can run it on your laptop, in your stack, on your clock.

The Cursor agent’s post-mortem ended with “I didn’t verify, I didn’t check.” That sentence is fair as a description of the agent, and it’s also fair as a description of every system the agent touched, which let it do exactly what it did. We don’t think the answer to that post-mortem is a smarter agent. We think the answer is a system that says no, with reasons, before the database is gone.
